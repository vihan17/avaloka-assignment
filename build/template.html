Section 1Problem 1 — O(1) LRU Cache

Both operations must be constant time with respect to cache size, so neither may scan the cache. That single constraint decides the data structures.

The short version

A hash map for lookup, a doubly linked list for order, and two sentinel nodes to delete the edge cases. Every operation touches a constant number of nodes no matter how full the cache is.

1.1  Approach: two structures, one job each

A cache is asked two different questions, and they are not the same question. The first is given this key, where is its entry? The second is which entry has gone unused the longest? A hash map is excellent at the first and has no opinion about the second. A linked list or an array is excellent at the second and needs a linear scan for the first. The whole exercise is about refusing to make one structure do both.

So I gave each question to the structure that answers it natively, and stored a link between them. The dictionary maps a key to the node that holds it, so a lookup never walks the list. The nodes form a doubly linked list in recency order, so once a node is in hand, moving it costs a fixed number of pointer writes. The dictionary is what makes get independent of how many entries the cache holds. The prev pointer is what makes removal independent of where the node sits.

Order runs from most recently used at the front to least recently used at the back. A hit in get moves its node to the front and returns the value; a miss returns -1 and changes nothing. put either overwrites an existing node and refreshes its position, or creates a node at the front — and if the dictionary was already at capacity, the node at tail.prev is unlinked and its key deleted from the dictionary. Each node stores its own key for exactly that last step: eviction holds a node, and turning a node back into a key would otherwise require a scan.

Both ends of the list are guarded by sentinel nodes that never hold data. They exist to remove branches. Without them, insertion and removal need separate cases for an empty list, for the head and for the tail — the three places where hand-written LRU caches usually break. With them, head.next and tail.prev always point at a node object, and the same four assignments work at every position. Two extra objects buy a hot path with no conditionals.

A note on what I did not use. Python's OrderedDict is this exact structure implemented in C, and functools.lru_cache is the standard production answer; both are faster than this code. I wrote the pointers by hand because the assignment is about the mechanics, and because the invariant worth testing — that the dictionary and the list describe the same keys in the same order — is invisible behind move_to_end.

1.3  The cases that break naive versions

Most incorrect LRU caches are wrong in one of these five places. They are listed here because each one is a test in the suite, not because the code is defensive.

put a new key while full Evict exactly one entry, then insert The check is len == capacity and happens before the insert; tail.prev is unlinked and its key removed from the map.

Section 2Problem 2 — Event Scheduler

Both functions answer the same underlying question — how many events are alive at once — so both are built on one sorted sweep and one convention.

The short version

Sort by start time and sweep once. The overlap check keeps the furthest end seen so far; the room count keeps a min-heap of end times, and its maximum size is the peak concurrency. The peak is the answer, because no schedule can beat it and a greedy one never exceeds it.

2.1  One convention: half-open intervals

Every event is treated as the half-open interval [start, end). The convention does two things at once. It encodes the brief's rule that an event ending at 10 and an event starting at 10 do not conflict, and it turns “is this room free?” into one comparison, end <= start, with no special case anywhere. Both functions share the convention, so a schedule that can_attend_all accepts is a schedule min_rooms_required counts as one room. They cannot disagree.

2.2  can_attend_all: is the diary free?

Sort by start time, then make a single pass while remembering furthest_end, the latest moment at which the person is still busy. An event can be attended only if it starts at or after that moment. If it starts earlier, it collides with something already seen. After each event, furthest_end = max(furthest_end, end), so the value never moves backwards even when a later event finishes sooner.

Keeping the running maximum, rather than comparing each event with its immediate predecessor, is what makes nesting free: in [(9, 12), (10, 11)] the second event ends before the first, but it starts before furthest_end = 12 and is caught without a separate containment rule. The strict comparison start < furthest_end is the adjacency rule: equal values are allowed.

Complexity. O(n log n) time, dominated by the sort; O(n) space for the sorted copy. An empty list returns True — nobody has a conflict.

2.3  min_rooms_required: count the peak

The key observation is that the answer is the peak concurrency. If k events are in progress at the same instant, no schedule can use fewer than k rooms, because each of them needs a distinct room at that instant. That is the lower bound, and it is easy. The upper bound is the useful half: a greedy sweep never opens a k+1-th room, because it only opens a room when every existing room is busy — and at that moment the new event plus the ones occupying those rooms are all in progress together, so the peak is at least the number of rooms it is about to exceed. If the peak is k, greedy never needs more than k. Minimum and maximum concurrency are the same number.

The implementation keeps a min-heap of end times for the rooms in use. Events are processed in start order. Before seating an event, every room whose end is at or before the current start is popped — because the heap is ordered by end time, one while loop releases all of them. Then the current end is pushed. The heap now holds exactly the events in progress at this start time, so its size is the concurrency at that instant.

Event Heap before Released Heap after Rooms in use
(0, 30)[]—[30]1
(5, 10)[30]—[10, 30]2
(15, 20)[10, 30]10[20, 30]2

Peak is 2, and two rooms really are enough: the all-day event keeps one room while the two short events share the other. For the brief's [(9,10), (10,11), (11,12)], every event releases its room before the next one starts, so the heap never holds more than one entry and the answer is 1.

A classical alternative avoids the heap entirely: sort starts and ends into two arrays and walk them with two pointers, opening a room when the next start precedes the current end and closing one otherwise. “Expected” is the honest qualifier. The linked-list work is O(1) in the worst case, but the dictionary probe is O(1) only on average: adversarial keys can collide and degrade a probe to O(n). Sorting is the floor for both functions: comparison-based sorting is Ω(n log n), and any algorithm that needs global order inherits that bound. There is one escape worth knowing: if times are small integers — minutes in a week, for instance, where T = 10,080 — a counting or bucket sort replaces the comparison sort, giving O(n + T) time at the cost of O(T) memory. For a meeting platform that is effectively linear and often the right trade; for arbitrary timestamps, the O(n log n) version is the general one.

3.2  Trade-offs: why a hash map plus a doubly linked list

The pairing is not a trick; it is the only arrangement in which both operations are O(1) without extra bookkeeping. The two structures answer complementary questions, and each one is cheap only because the other exists. A dictionary alone can find a value but cannot find the oldest one without a scan. A list alone can find the oldest one instantly but cannot find a key without a scan.

StructureLookupEvict LRUWhy it is not enough
Hash map onlyO(1)O(n)No order; finding the oldest means scanning every entry, or storing timestamps and scanning for the minimum.
Array + hash mapO(1)O(n)Moving an entry to the front shifts every element after it.
Singly linked list + mapO(1)O(n)Unlinking needs the predecessor, and a singly linked node does not know it.
Hash map + doubly linked listO(1)O(1)—
Hash map + min-heap by timestampO(1)O(log n)A log factor per eviction, a monotonic counter per entry, and no stable tie-breaking.
OrderedDictO(1)O(1)The same design in C: faster, but it hides the mechanics and does not port to languages without an ordered map.

Why doubly linked and not singly linked. To remove a node from a singly linked list you need the node before it, and finding that node means walking from the head — O(n), which destroys the guarantee at exactly the moment it matters, during eviction. A prev pointer makes removal independent of position: four assignments, no search. Keeping a separate “predecessor” dictionary would also work, but it costs another hash lookup and more memory than a pointer that is already there.

What the combination costs. Each entry carries two pointers and a dictionary slot, so memory is roughly double a bare dictionary — measured at {{B_BYTES}} bytes per entry here. Nodes are separately allocated, so a get touches a dictionary bucket, then the node, then its two neighbours: three or four cache lines in unrelated places. At ten thousand entries that is noise; at fifty million it is the dominant cost, and it is why high-throughput caches avoid a global linked list. The structure is also hostile to lock-free concurrency, because every eviction mutates shared neighbours (see 3.4).

Why not always exact LRU. LRU is a good policy for locality, not a universally good one. A sequential scan of one-off keys evicts everything useful, and against an adversarial access pattern LRU can be arbitrarily worse than Belady's offline optimum. Production systems therefore approximate it: CLOCK / second-chance keeps a reference bit instead of a list, 2Q and segmented LRU add a probationary segment so scans cannot flush the hot set, and Redis samples a handful of keys and evicts the oldest among them rather than maintaining a global order. Each of those gives up exactness for locality, memory or throughput — the same trade-off this exercise makes in the other direction.

3.3  Future proofing: assigning room numbers

Counting rooms is not the same as naming them. The sweep already knows which rooms are free at each start time, so the change is to carry identities instead of a count: one heap of free room ids, and one heap of (end, room id) for busy rooms. When an event starts, every room whose end is at or before that start moves from the busy heap to the free heap; the event then takes the smallest free id, or mints a new one. The result is deterministic, reuses the lowest-numbered room available, and uses exactly min_rooms_required rooms.

The greedy is optimal for the same reason as the count: a new room is opened only when the free heap is empty, which means every existing room is busy at that instant, so the number of rooms in use is a lower bound on the peak. Choosing the smallest free id rather than an arbitrary one changes only the labels, never the number of rooms or the feasibility of the schedule.

Two details make it usable rather than merely correct. If the caller needs the answers in its own order instead of chronological order, sort by (start, end, original index) and write into a preallocated result list; that is a two-line change which does not touch the sweep. And labels are generated in bijective base-26, so the sequence continues past Z without collisions: Room A … Room Z, Room AA, Room AB ….

In a real platform the same sweep would need more state, and at some point greedy stops being enough:

  • Resources. Projectors, capacity or accessibility turn room choice into a constraint-satisfaction problem, and the greedy assignment is no longer guaranteed optimal; a bipartite matching or a small ILP is the honest tool.
  • Buffers. Ten minutes to reset a room is just an inflated end time, end + buffer, which the existing comparison already handles.
  • Time zones and DST. Store UTC instants rather than wall-clock integers; a half-open interval over datetime behaves exactly like the integer version.
  • Recurring events. Expand the recurrence rule over a bounded horizon, then schedule the expanded instances.
  • Fairness. Replacing “smallest free id” with “least-used room” spreads wear and keeps premium rooms available; it is a different heap key, not a different algorithm.
  • Correctness under concurrency. Two requests must not book the same room at once. A database exclusion constraint on (room_id, tstzrange(start, end)) enforces the invariant where it matters, rather than trusting the scheduler process to be the only writer.

3.4  Concurrency: making the cache thread-safe

The first thing to notice is that get is not a read. A hit reorders the linked list, so every lookup is a mutation. That rules out the reflex answer of “wrap it in a readers-writer lock”: every get would need the write lock, and the lock would serialise exactly as much as a plain mutex while adding overhead.

Without a lock, several failure modes are reachable. Two threads can both observe a full cache and each evict a different node for one insertion, so the cache silently shrinks. A node can be detached twice, leaving its neighbours pointing at each other incorrectly. A thread can hold a reference to a node that another thread has just evicted and reinsert it, producing a node that is in the list twice or a key that points to a node no longer in the list at all. The GIL does not prevent any of this: it switches between bytecodes, and the window between the dictionary probe and the four pointer writes is many bytecodes wide.

One mutex around both operations is correct, simple, and enough for most services. It also has to cover compound operations: “get, and on a miss compute and put” is not atomic just because each half is. Keep the critical section short, and never call user code — a loader, a network call, a callback — while holding the lock.

When a single lock becomes the bottleneck, the practical answer is sharding, not finer-grained locking of the same list: the list is one global order, so every eviction touches nodes that other operations also touch, and per-node locks would need hand-over-hand locking across four nodes. Sharding gives each shard its own list, lock and slice of the capacity, so different shards never contend. The price is per-shard eviction, which makes the global policy approximate: a hot key that hashes to a cold shard can be evicted before a cold key in a hot shard. hash(key) % shards spreads typical keysets evenly, so this is usually acceptable — but it is a behavioural change, not just a performance one.

At larger scale the same idea appears in different clothes. Redis keeps a 24-bit access clock per key and evicts the oldest of a small random sample, which avoids a global list entirely. Caffeine records reads in a striped, lock-free buffer and replays them into the eviction policy asynchronously, so recency is eventually consistent in exchange for scalability. Both accept a small amount of policy error to remove the contention that an exact global order creates.

I verified the wrapper rather than assuming it: eight threads × 4,000 random operations, with sys.setswitchinterval(1e-6) to force frequent preemption, then a white-box check that the map and the list contain the same keys in the same order, that the size is exactly the capacity, and that every prev/next link is consistent. A stress test cannot prove the absence of a race; it can only make one likely to appear, which is why the invariant check is the part that matters.

One boundary worth naming: this lock protects threads inside one process. An asyncio.Lock is the coroutine equivalent but does not protect threads, and a cache shared between processes needs a shared server — Redis or Memcached — where writes are serialised by construction.
